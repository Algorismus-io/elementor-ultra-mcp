## Summary

Companion-plugin PHP for the Pro Theme Builder surface: the shared Pro REST controller bootstrap (route registration, Pro/experiment gate, error mapping), a `Conditions_Helper` that writes display conditions ONLY through `Conditions_Manager::save_conditions()`, and a `Theme_Builder_Service` that creates the typed theme-builder documents (header/footer/single-post/single-page/archive/search-results/error-404/section) and exposes the conditions-config tree. This WP owns `class-pro-controller.php` (the registration hub all other WP-R PHP packages register their routes against via a shared registry method) plus the theme-builder slice; popup/form/loop/dynamic/woo route handlers live in sibling WPs that register through this controller.

## Interface / Contract

Implements REST routes (Contract 10 §8.1-§8.3), namespace `elementor-ultra/v1`:

- `POST /pro/theme` — CAP_EDIT_POST — create a theme-builder document.
- `PUT  /pro/theme/{id}/conditions` — CAP_EDIT_POST — replace all display conditions.
- `GET  /pro/theme/conditions-config` — CAP_READ — conditions-config tree.

Shared controller surface (consumed by WP-R02..WP-R06 PHP siblings):

- `class Pro_Controller` registers ALL `/pro/*` routes via `register_routes()`. To keep `files_owned` disjoint, sibling WPs do NOT edit this file; instead `Pro_Controller::register_routes()` instantiates the per-domain service classes (`Popup_Service`, `Form_Builder_Service`, `Loop_Service`, `Dynamic_Tags_Service`, `Woo_Service` — owned by sibling WPs) and registers their routes by calling each service's public `routes(): array` method, which returns an array of `[method, path, callback, permission_callback, args]` descriptors. This WP defines that descriptor contract and the `Pro_Controller` loop; siblings provide the service class + its `routes()` array. The controller file therefore changes ONLY when a new service class is added — handled by appending one line per sibling WP; to avoid contention this WP ships the full list of six service classes up front (theme handled inline; the other five wired as `class_exists()`-guarded `require`-then-`->routes()` so the controller is complete even before siblings land, degrading gracefully when a sibling service file is absent).

`Pro_Gate` (shared): `Pro_Gate::require_pro()` returns `WP_Error` `E_FEATURE_UNAVAILABLE` (HTTP 501, taxonomy `PRO_REQUIRED`) with `data.meta.{pro_active,experiment}` when Pro inactive; `Pro_Gate::require_experiment($slug)` likewise for an inactive experiment (`EXPERIMENT_INACTIVE`). Every `/pro/*` permission_callback runs the cap check; every handler first-lines `Pro_Gate::require_pro()`.

`Conditions_Helper` (shared by theme + popup):
- `save(int $post_id, array $tuples): array` — converts `ConditionTuple[]` (`[type,name,sub_name?,sub_id?]`) to the manager's `[[type,name,sub_name,sub_id], ...]` form, calls `Conditions_Manager::save_conditions()` (which writes slash strings + `cache->regenerate()`), and returns the stored slash strings `conditions_stored` by re-reading `_elementor_conditions`.
- `validate(array $tuples): WP_Error|true` — `type ∈ {include,exclude}`; reject `single` doc type is handled at the doc layer (not here); validate `name`/`sub_name` against `get_conditions_config()` keys (warn-not-fail for site-specific CPT/tax names — see Detailed Requirements).
- `conflicts(int $post_id, array $tuples, string $location): array` — wraps `Conditions_Manager::get_conditions_conflicts_by_location()`.

`Theme_Builder_Service`:
- `routes(): array` — descriptors for the three routes above.
- `create(array $params): array|WP_Error` and `set_conditions(...)`, `conditions_config(): array`.

## Detailed Requirements

1. **Controller registration.** `Pro_Controller::register_routes()` hooks `rest_api_init`. It builds the route table by merging this WP's three theme routes with the `routes()` arrays returned by the five sibling services. Each sibling service file is loaded with `if ( file_exists(...) ) require_once ...; if ( class_exists(...) ) $services[] = new ...;` so a missing sibling file does not fatal. The descriptor shape is FROZEN here: `[ 'methods'=>WP_REST_Server::CREATABLE|READABLE|EDITABLE, 'route'=>'/pro/...', 'callback'=>callable, 'permission_callback'=>callable, 'args'=>array ]`.

2. **Pro/experiment gate.** Every `/pro/*` handler MUST first call `Pro_Gate::require_pro()`. Return 501 `E_FEATURE_UNAVAILABLE` with `data.meta = { pro_active:false }` (or `{ experiment:'e_pro_atomic_form' }` for the atomic-form path, deferred to WP-R03). Use `defined('ELEMENTOR_PRO_VERSION')` / `class_exists('ElementorPro\\Plugin')` for Pro presence.

3. **`POST /pro/theme`.** Validate `type ∈ {header,footer,single-post,single-page,archive,search-results,error-404,section}`. Explicitly REJECT `type='single'` → 400 `E_BAD_REQUEST` (`data.meta.reason='single is hidden/legacy; use single-post/single-page'`). For `type='section'`, `location` is REQUIRED and MUST exist in `get_locations_manager()->get_locations()` else 400. Behaviour order (SUPPLEMENT §A.7 pro.theme.create): (a) `documents->create($type, ['post_title'=>title,'post_status'=>status], $type==='section' ? ['_elementor_location'=>location] : [])`; (b) if `elements` present, run `Validator::dry_run()` (WP-P03) — on failure return 422 `E_ATOMIC_VALIDATION` and DELETE the just-created draft (compensation) so a failed validate leaves no orphan; (c) persist via the WP-P04 `Document_Writer` (`Document::save(['settings'=>page_settings,'elements'])`); (d) if `conditions` present, `Conditions_Helper::save()`. Response `data` per §8.1: `{ post_id, edit_url, template_type, location, conditions_stored }`.

4. **`PUT /pro/theme/{id}/conditions`.** REPLACES all conditions; `conditions:[]` clears (manager deletes the meta). If `check_conflicts:true`, compute `conflicts` per condition via `Conditions_Helper::conflicts()` for single-instance locations (header/footer/single) and return them BEFORE saving only if the caller is in conflict-preview mode — but the contract (§8.2) returns conflicts ALONGSIDE a successful save, so: compute conflicts, then save, then return both. Popup location is `multiple=true` → never conflicts. Response: `{ saved, conditions_stored, conflicts? }`.

5. **`GET /pro/theme/conditions-config`.** Return `Conditions_Manager::get_conditions_config()` as `tree`, plus `id_bearing: string[]` listing which sub-condition names take a `sub_id` (derive from SUPPLEMENT §A.1: `post`→post_id, taxonomy/in_taxonomy→term_id, author/by_author→author_id, child_of/any_child_of→parent_id). Response: `{ tree, locations }` where `locations` = `get_locations_manager()->get_locations()` keys (or per §8.3 also expose `id_bearing`).

6. **Conditions tuple → manager form.** `Conditions_Helper::save()` MUST pass the manager an array of arrays WITHOUT an `_id` key (the manager `unset($condition['_id'])`), i.e. positional `[type,name,sub_name,sub_id]` with trailing empties allowed (manager `rtrim`s the slash join). After save, re-read `get_post_meta($id,'_elementor_conditions',true)` to populate `conditions_stored` (the canonical slash strings) — do NOT re-derive them in PHP, trust the stored value.

7. **Validation of names.** `Conditions_Helper::validate()` checks `type` strictly; for `name`/`sub_name` it cross-checks `get_conditions_config()` keys and returns a `WP_Error` only for a structurally impossible tuple (e.g. `type` not in enum). Unknown site-specific CPT/taxonomy names are PASSED THROUGH (the site may register them), not rejected — but recorded into `data.meta.unverified_names[]` for the caller. NEVER hardcode beyond the core catalog (SUPPLEMENT §A.1).

8. **Woo gotcha note.** When WooCommerce is active, `product`/`product_archive` conditions do not fire for theme docs (`theme-builder/module.php:44-46`, `conditions/archive.php:50-53`). The helper appends a `data.meta.warning` when a saved condition names `product`/`product_archive` and Woo is active. Non-fatal.

9. **Error mapping.** Use the WP-F05 `ErrorPayload`/`WP_Error` builder. Map: missing/invalid `type` → `E_BAD_REQUEST` (400); post not found → `E_NOT_FOUND` (404); not editable → `NOT_EDITABLE` (403, `document.php:821`); validation fail → `E_ATOMIC_VALIDATION` (422); Pro inactive → `E_FEATURE_UNAVAILABLE` (501). Never string-match Elementor throws (§0.6).

10. **Op-log + idempotency.** All three write routes accept `op_id` and write one op-log row (delegated to the op-log store (ops controller) via the shared writer used by WP-P04). Theme `create` is non-idempotent (each creates a new post) but records `op_id`; `set_conditions` is idempotent (replace semantics).

## Implementation Notes

- Keep `Pro_Controller` thin: registration + the descriptor loop only. All theme business logic lives in `Theme_Builder_Service`; conditions logic in `Conditions_Helper`. This lets WP-R02 (popup) reuse `Conditions_Helper` by depending on this WP without editing its files.
- Document creation for theme types uses the SAME `Document_Writer` (WP-P04) so backup-before-write, base_hash, lock/autosave, and prime-css all flow identically. Theme docs that carry an atomic `elements` tree MUST set `prime_required:true` in the response and accept `prime_css:true` to chain priming (WP-P05) — reuse the writer's existing prime hook; do not reimplement.
- `get_type()` is canonical for the slug (SUPPLEMENT §A.1) — after `documents->create()`, read `$doc->get_type()` for `template_type` rather than echoing the request `type`.
- Conflict detection: `get_conditions_conflicts_by_location($condition, $location, $ignore_post_id=$post_id)` — pass the current post id as `$ignore_post_id` so a doc never conflicts with itself.
- Gotcha: `save_conditions()` with an EMPTY array DELETES `_elementor_conditions` and still calls `cache->regenerate()` — relied on for the `[]`-clears semantics.
- PHPCS WordPress + WordPress-Extra clean; every Elementor call carries a `path:line` comment.

## Acceptance Criteria

- [ ] `POST /pro/theme` creates each of the 8 valid types; `template_type` in the response equals `$doc->get_type()`.
- [ ] `type='single'` → 400 `E_BAD_REQUEST` with a `reason` meta; no post is created.
- [ ] `type='section'` without a valid `location` → 400; with a valid location, `_elementor_location` meta is set.
- [ ] A theme `create` with an invalid atomic `elements` tree returns 422 `E_ATOMIC_VALIDATION` AND no orphan draft remains (compensation deletes it).
- [ ] `conditions` on create are stored as slash strings (verified by reading `_elementor_conditions`) and `cache->regenerate()` ran (CSS cache cleared).
- [ ] `PUT /pro/theme/{id}/conditions` with `[]` deletes the meta; with tuples, replaces it; `conditions_stored` matches stored slash strings byte-for-byte.
- [ ] `check_conflicts:true` returns conflicts for a duplicate header include and an empty list for a popup-location condition.
- [ ] `GET /pro/theme/conditions-config` returns the live `get_conditions_config()` tree + `id_bearing` list; no hardcoded CPT/tax names.
- [ ] Every `/pro/*` route 501s with `E_FEATURE_UNAVAILABLE` when Pro is inactive (probe via a Pro-off wp-env).
- [ ] `Pro_Controller::register_routes()` registers the three theme routes plus, when sibling service files exist, their routes — and does not fatal when they are absent.
- [ ] PHPCS clean; every Elementor call has a `path:line` comment.
